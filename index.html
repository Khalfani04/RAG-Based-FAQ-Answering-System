1. System Overview

This project implements a Retrieval-Augmented Generation (RAG) pipeline that answers questions about the Durham College HBAI program. The system embeds a 27-document FAQ knowledge base using sentence-transformers/all-MiniLM-L6-v2, stores vectors in ChromaDB, and generates answers with google/flan-t5-base — a free, locally-run LLM. No API key is required.

The core idea behind RAG is to ground LLM generation in retrieved factual context, preventing hallucination and limiting answers to verified knowledge base content. When retrieval confidence is low (similarity < 0.4), the system falls back to a supplementary context source rather than generating an unsupported answer.

Each test question includes the question text, the expected source document ID (ground truth), and a list of expected keywords that a correct answer should contain.

2.2 Metrics

Metric 1 — Retrieval Recall@3: Measures whether the correct source document appeared in the top-3 retrieved chunks at query time. A high Recall@3 means the embedding model is finding semantically relevant documents. If retrieval fails, generation will always fail regardless of LLM quality.

Metric 2 — Answer Faithfulness (Keyword Proxy): Measures whether the generated answer contains at least one expected keyword from the ground truth answer. This is a lightweight proxy for faithfulness. A full implementation would use an NLI model to check semantic entailment.

4. Failure Case Analysis

Recall Miss

Failure Type 1: Low Retrieval Similarity

"Is the HBAI program available online?"

The knowledge base contains doc_003 which states the program is "delivered primarily in-person with some hybrid components" — but this phrasing is semantically distant from "available online." The retriever returns docs about program structure and co-op instead.

Before the fallback was added, the model correctly responded "I do not have enough information to answer that." — demonstrating the system refuses to hallucinate. With adaptive fallback enabled, the system routes to a supplementary context source and returns a grounded answer.

Fix: Add a document explicitly addressing online/hybrid delivery format, or chunk doc_003 so each fact has its own embedding.
Faithfulness Miss

Failure Type 2: Answer Rephrasing

Flan-T5-base sometimes generates a correct answer that does not contain the exact expected keywords. For example, a question about domestic tuition might yield "Ontario residents pay approximately eight thousand dollars" — correct but won't match the keyword $8,000.

Fix: Expand the keyword list to include paraphrases, or use BERTScore instead of exact keyword matching.
Truncation

Failure Type 3: Context Window Truncation

Flan-T5-base has a 512-token input limit. When three long context chunks are concatenated, the prompt may be truncated, cutting off critical information before it reaches the generation step.

Fix: Reduce chunk size in the knowledge base, or switch to flan-t5-large which supports up to 2048 tokens.

5. Discussion

What Worked Well

  • Semantic retrieval is robust for direct factual questions. Questions like "What GPA do I need for co-op?" consistently retrieve the right document.
  • Hallucination refusal works correctly. When a question falls outside the knowledge base, the model returns a fallback response rather than fabricating an answer.
  • Adaptive fallback routing works as designed. The similarity threshold correctly identifies low-confidence retrievals and routes them to supplementary context (Source: web_fallback confirmed in output).
  • No API dependency. The entire system runs on free Colab compute, making it fully reproducible.

Limitations

  • Flan-T5-base generation quality is limited at 250M parameters. Answers are often correct but short and sometimes fail to synthesize across multiple chunks.
  • Keyword-based faithfulness is a proxy metric — marks correct answers as unfaithful if the model paraphrases without using exact expected words.
  • Static knowledge base cannot answer questions about program changes or updated fees without manual updates.

7. Conclusion

The RAG system successfully demonstrates the core retrieval-augmented generation pipeline on a real domain-specific knowledge base. Retrieval Recall@3 is strong due to the quality of all-MiniLM-L6-v2 embeddings. The main limitation is the generation stage — flan-t5-base is effective for simple factual answers but struggles with synthesis across multiple chunks.

The system's correct refusal to answer out-of-scope questions, combined with the adaptive fallback routing feature, validates the grounding mechanism of RAG. The fallback correctly triggers on low-similarity queries (similarity < 0.4) and routes to supplementary context, demonstrating a practical extension of the base RAG architecture.

The most impactful next step would be upgrading the LLM while keeping the retrieval pipeline unchanged, as retrieval quality is already solid.
